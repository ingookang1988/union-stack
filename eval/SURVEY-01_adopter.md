# union-stack 어답터 설문 v1 — 이 레포의 에이전트에게

## 왜 묻는가 (1분)

상류 union-stack 은 하네스를 **사용처에서** 검증하려 한다. 상류 레포의 연습 과제에서 좋아 보이는 규칙이 어답터에서도
작동하는지는 어답터만 안다(2026년 하네스 진화 문헌 4편의 공통 결론: 측정에서 이긴 변경이 사용처로 옮겨지지 않는다).
세 가지를 받으려 한다.

1. **프로필** — 이 레포·팀·제품이 어떤 형상인지(답을 형상별로 나눠 읽기 위해).
2. **계측** — 하네스 도구의 **출력 원문**(정량은 자기보고가 아니라 계측기에서).
3. **증언** — 행동에 고정된 정성 답(우회 사례·마찰·제거 후보·제안).

결과는 상류의 제거·추가·축 제안(PRO 후보)과 상류 `[PRO-22]`(테스트 축) · `[PRO-23]`(채택 자격) 판정으로 간다.

## 실행 모드 — 답변 머리에 하나를 적는다

| 모드 | 누가 | 답하는 절 |
|---|---|---|
| **U (사용 모드)** | 이 레포에서 세션 이력이 있는 에이전트(전사·메모리 보유) | §0 ~ §6 |
| **C (냉독 모드)** | 이 레포에서 **작업한 적 없는** 모델·도구 | §0 · §1(1-4·1-5 제외) · §3 · §4 · 5-0 · 5-7 · §7 — 경험 문항은 비운다 |

한 레포에 여러 도구가 답한다. 각 도구는 **자기 도구의 이력**으로 U/C 를 정한다(이 레포에 Claude Code 세션이 많아도
이 도구로는 처음이면 C).
문항 태그: `[U]` 사용 모드 전용 · `[C]` 냉독 모드 전용 · `[U/C]` 둘 다.
**C 모드는 경험을 지어내지 않는다.** 경험 문항은 비워 두고 §7 의 부트스트랩 기록으로 답한다.

## 답변 규칙

1. **조사는 읽기 전용.** 이 설문 파일은 고치지 않는다. 답은 같은 폴더의 **`SPIKE-harness_adopter_survey.answer.<도구>.md`**
   (도구 = `claude` · `chatgpt` · `antigravity` 처럼 소문자 한 단어)에 쓴다 — 머리 형식은 맨 아래 `## 답변` 절.
   테스트·CI·설정·평면 문서는 고치지 않는다. **같은 폴더의 다른 `*.answer.*.md` 는 열지 않는다**(블라인드 — 도구 간
   교차 비교가 목적이다. 이미 열었다면 답변 머리에 그 사실을 적는다).
2. **파괴적 명령 금지** — DB 쓰기·마이그레이션·원격 쓰기·유료 호출. 계측기는 아래에 적힌 읽기 전용 호출만 쓴다
   (`--write`·`--apply` 금지). 테스트 실행이 꼭 필요하면 비파괴 스위트만, 확신이 없으면 "미실행".
3. 문항마다 **사실**(경로·커밋·수치) · **의견** · **확신도**(높음/중간/낮음). 모르면 "모름" — 추측 금지.
4. **근거 경로가 없는 칭찬·비판은 집계에서 제외된다.** 좋다/나쁘다 대신 "언제 무엇이 일어났나"를 적는다.
5. **장점 1개마다 반례 1개** — 또는 "반례 없음 — 찾아본 범위: …".
6. 인간의 판단·선호가 필요한 문항은 **"인간 확인 필요"** 로 표시하고 넘어간다.
7. 커밋·푸시·상류 이슈 생성은 하지 않는다(인간 승인 사항).
8. 상류 ID 는 `상류 [PRO-22]` 처럼 적어 이 레포의 로컬 ID 와 구분한다.
9. §6 의 관측은 **상류 감사 에이전트의 판독**이다 — 틀린 것은 정정해 주는 것이 답변의 일부다.
10. 계측기 출력은 **원문 그대로** 펜스 블록에 붙인다. 요약하지 않는다. 스크립트가 없으면 "도구 없음(템플릿 버전 …)".
11. **시간 상자**: U 약 2시간 · C 약 1.5시간. 전부 못 하면 아래 순서로.
    U: §0 → §1 → §3 → 5-6 → §2 → §4 → §5 나머지 → §6
    C: §0 → §7 → §1 → §3 → 5-0·5-7 → §4
12. **경계**: 답변은 이 레포의 spike 에 남는다. 상류에는 **익명 집계**만 옮긴다. 이 레포의 내용을 레포 밖
    (다른 제공사의 모델 등)으로 보내는 범위는 **인간이 정한다** — 에이전트가 넓히지 않는다.

## §0 프로필 `[U/C]`

- **0-1 제품**: 한 줄 설명 · 도메인 · 단계(프로토타입 / 베타 / 운영) · 사용자 규모 등급(내부용 / <100 / <10k / 그 이상).
- **0-2 코드**: 언어·프레임워크 · 규모(`git ls-files | wc -l`, LOC 대략) · 모노레포 여부·패키지 수 · 저장소 나이(첫 커밋).
- **0-3 사람·에이전트**: 사람 수 · 쓰는 에이전트 도구와 모델(Claude Code / Codex / Gemini CLI / Cursor / 기타) ·
  최근 100 커밋 중 에이전트 커밋 비율(트레일러·작성자로 추정) · 사람이 에이전트 결과를 리뷰하는 방식.
- **0-4 하네스 버전·동기화** — **필수.** 모든 답은 이 값으로 태깅해 읽는다(구버전이면 "없는 기능" 지적은 버전 간격으로 먼저 설명된다).
  - 0-4-1 도입 시기: `git log --diff-filter=A --reverse --format=%cs -- .union-stack` 의 첫 줄.
  - 0-4-2 현재 버전: `CHANGELOG.md` 최신 헤딩(`[Unreleased]` 가 있으면 그 다음 것). 없으면 "CHANGELOG 없음".
    상류의 최신 **발행** 버전과 미발행 변경 유무는 §6-0 에 적혀 있다.
  - 0-4-3 최근 동기화 날짜: `.union-stack/template-sync.json` 이 있으면 그 `ref` 와
    `git log -1 --format='%cs %h' -- .union-stack/template-sync.json`. 없으면 템플릿 소유 파일이 마지막으로 바뀐 커밋:
    `git log -1 --format='%cs %h %s' -- CHANGELOG.md scripts/ .github/workflows/harness.yml`.
  - 0-4-4 간격: 상류 기준(§6-0)과 몇 버전·며칠 차이인지. 1-6 이 돌면 그 출력이 정본이다.
  - 0-4-5 **이전 방식**(없음 / CLAUDE.md 단일 / cursor rules / 자체 체계) · 로컬 개조(로컬 PRO·ADR·도구·스킬 수).
- **0-5 평면 크기**: 도메인별 문서 수(1-1 출력에서) · 원장 ADR 수 · LSN 수 · 로컬 PRO 수 · WO 수(상태별).
- **0-6 (C 모드)**: 이 도구·모델 이름과 버전, 이 레포를 처음 본 시각.

## §2 경험 `[U]` — 행동에 고정

- **2-1 실제로 쓴 것**: 최근 30일(또는 10세션)에 호출한 하네스 도구·스킬·의례와 횟수(1-4 와 대조). **한 번도 안 쓴 것** 목록.
- **2-2 이전 방식 대비**: 지금 하네스를 걷어내고 0-4 의 이전 방식으로 돌아가면 **잃는 것 3개**(각각 사례 경로)와
  **얻는 것**(줄어드는 마찰). 반례 규칙(5번) 적용.
- **2-3 우회 사례**: 규칙을 우회·무시·형식만 맞춘 최근 사례 3건(커밋·WO) — 이유(시간 / 무의미 / 이해 못함 / 다른 규칙과 충돌).
- **2-4 마찰**: 1-5 의 상위 5 항목과 대조해 "하네스 **때문에** 생긴" 마찰과 "하네스가 **줄인**" 마찰을 가른다.
- **2-5 오라우팅**: HANDOFF·LSN·ADR·PRO·HISTORY 중 엉뚱한 곳에 적었다가 옮긴 사례, 또는 어디 적을지 몰라 **안 적은** 사례.
- **2-6 묻힌 규칙**: 1-2 의 부트스트랩 토큰 실측 + 긴 세션에서 초반 규칙을 후반에 어긴 커밋(있으면).
- **2-7 병렬**: 서브에이전트·worktree·여러 에이전트 동시 작업 사례와 충돌(같은 계보 동시 편집) 여부.
- **2-8 차별점**: 다른 레포·도구에서 못 본 것 1~3개. 반례 규칙 적용.

## §3 제거 `[U/C]` — 추가보다 먼저 (상류는 제거 기계다 — 상류 [ADR-12])

- **3-2 지우면 안 되는 것 3개**와 그 이유가 된 **사건**(경로·커밋).

- **4-1 빠진 축**: 이 레포에서 반복되는데 평면 어디에도 자리가 없는 사실·결정의 종류

- **4-4 하류 자체 발명**: 이 레포가 스스로 만든 방어·도구·절차 중 상류 표준화 후보(코드 경로).
- **4-5 다른 도구·모델**: Claude Code 외 도구에서 AGENTS.md 가 작동한 경험 / 실패.

## §5 테스트 축 `[U]` — 상류 [PRO-22] H1~H5 · [PRO-23] 실행 가능성 (5-0 · 5-7 은 `[U/C]` — 레포 사실만으로 답한다)

상류 가설 5개 — 각각에 **사례 또는 반례**를 모은다.
- **H1 실행**: 어떤 검사가 실제로 막는지가 선언돼 있지 않아서, 꺼져도 모른다.
- **H2 영수증**: 증거가 실행 산출물이 아니라 에이전트 수기라 사후 검증이 안 된다.
- **H3 기준선**: 알려진 실패에 담당·만료가 없어 상주한다.
- **H4 약화**: 테스트 약화(삭제·skip·단언 감소·스냅샷 대량 갱신·mock 교체)가 diff 에 보이는데 아무도 묻지 않는다.
- **H5 카탈로그**: 테스트 자산 가시성(카탈로그)은 2차 문제다.

**5-0 맥락**
- 5-0-1. 이 레포의 테스트 층을 한 표로: 층(타입·린트·구조/아키텍처·단위·통합·E2E·평가·기타) | 명령 | 위치 | 대략 개수 |
  **실제로 누가·언제 돌리나**.
- 5-0-2. 위 표의 각 행을 네 종류로 분류해 보라 — **정적 검사**(실행 없이 형식) / **동작 검증**(실행해 기대값 비교) /
  **재현**(격리 환경에서 같은 결과) / **측정**(얼마나 좋은가, 분포). **어느 칸에도 안 들어가는 행**이 있으면 그것이 답이다.

**H1 실행**
- 5-1-1. 오늘 기준 머지·푸시를 **실제로** 막는 검사는? 문서상 막는다고 적힌 것과 다른가?
- 5-1-2. 검사가 꺼졌거나 안 돈 채 지나간 기간이 있었나? 어떻게 알게 됐나(또는 아직 모르나)?
- 5-1-3. 에이전트가 WO 를 닫을 때 "검사가 실제로 돌았다"를 무엇으로 확인하나?
- 5-1-4. 하네스가 **검사 선언 표**(이름·명령·차단 여부·실행 위치·종류)를 요구하면 유지하겠나? 꼭 필요한/불필요한 필드는?
  손으로 쓰는 표 vs `package.json`·워크플로·훅에서 생성 — 어느 쪽?
