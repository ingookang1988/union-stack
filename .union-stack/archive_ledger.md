# Architecture Decision Ledger
- (예시) [2026-01-01][ADR-01]: 결정화된 아키텍처 결정의 정수가 여기 1~2줄로 누적됨.
- [2026-08-20][ADR-42]: **두 번째 회전 수행 + [PRO-18] §3-2 의 60% 파라미터 판정 — 바꾸지 않는다.** 회전: ADR-26~33(8건) → `archive_ledger/ADR-26_33.md`(12.9KB), 머리 29.5→**17.0KB**. 성공 바 충족(미해소 ID 집합 37종 불변 · 차단 표식 6건 불변 · 보존 검사 통과 · 크기 초과 0). **판정의 근거는 파라미터가 아니라 입력이었다.** 실측 성장률: 2026-06-14~08-18 은 24건/67일 = **0.36건/일**, 엔트리 평균 **1,085B** → 약 390B/일. 그런데 2026-08-20 하루가 **16건 · 평균 2,244B** = 약 36KB/일로, **역사적 평균의 90배**다. 60% 목표(18KB, 헤드룸 12KB)는 역사적 속도에서 **약 31일치**를 준다 — 설계 의도("다음 세션이 다시 걸리지 않게") 그대로다. 즉 60%가 실패한 것이 아니라 **이 레포 역사상 가장 이상한 하루에 시험당한 것**이고, 이상치 1회로 영구 파라미터를 바꾸는 것은 이 레포가 다른 곳에서 금지하는 추론이다([PRO-11] §4 측도 금지 문법). 산술도 튜닝을 지지하지 않는다: 목표를 60%→40% 로 내려도 회전 *빈도*가 1.5배 줄 뿐 체제가 바뀌지 않고(헤드룸 12→18KB), 다세션 헤드룸을 얻으려면 목표를 4% 이하로 두어 사실상 매번 전부 옮겨야 한다 — 그건 파라미터가 아니라 머리의 정의를 바꾸는 일이다. **진짜 관측은 엔트리 크기 드리프트다**: 평균이 1,085(ADR-02~25) → 1,624(26~35) → **2,244B(36~41)** 로 2배가 됐는데, 원장 형식은 "결정의 **정수**가 1~2줄로 누적"이라고 선언한다. 크기가 역사적 평균이었다면 같은 60% 가 11건(≈2세션)을 담는다 — **파라미터가 아니라 입력이 계약을 벗어났다.** 자동화도 하지 않는다(§6 이 "두 번째 회전 때 논한다"고 건 항목): 정상 속도에서 회전은 월 1회 수준이고, [ADR-08]의 기준상 강제·자동화는 마찰 증거가 먼저인데 월 1회는 마찰이 아니다. 회전 자체는 이번에도 일회성 스크립트로 수행했다(스크래치패드). **다음 관측점**: 엔트리 평균이 1,500B 이하로 돌아오는지, 아니면 2,000B 대가 새 정상인지. 후자면 그때는 60% 가 아니라 **원장 형식(정수 vs 서술)** 이 판정 대상이다. **즉석 실증**: 이 항목 하나(2.3KB)가 회전 직후의 머리를 17.0 → 19.3KB 로 되돌려 목표(18KB)를 다시 넘겼다 — 엔트리 한 건이 헤드룸 12KB 의 **19%** 를 먹는다. 목표는 회전 *조작*의 정지 규칙이지 상시 불변식이 아니므로(트리거는 30KB 상한이다) 추가 회전은 하지 않았고, 대신 이 사실을 위 크기 드리프트 관측의 직접 증거로 남긴다.
- [2026-08-21][ADR-43]: **[PRO-19] 승인·이행 — 상류 가드 셋**(발행 린트 · 로드맵 배선 · 인계 진입점). 수명주기 가드가 전부 하류(종료, [PRO-15])에 있던 비대칭을 닫았다: ①`work-close --table` 이 활성 WO 의 발행 계약(3절 + 실존·계보 일치 `parent:`)을 CLARIFY 로 표면화 ②PHASE 를 `CONTEXT_DOMAINS` 편입 + `health` 에 roadmap wiring 관측(무연결/정체 — 쓰기는 강제 안 함, roadmap 은 Schema) ③`handoff-linter` 가 §3 의 `[WO-*]` 진입점 부재를 CLARIFY. 신규 스크립트 0(기존 3개 확장), REJECT 0. **가드를 먼저 물렸다([ADR-40] 절차)**: 수리 전 형상에서 넷 다 발현 — 예시 WO 의 죽은 부모(`PLAN-01a` 미실존 → `PLAN-01` 로 수리), 현행 HANDOFF §3 의 prose 이월(방치 — 다음 세션이 승격), roadmap 관측 무연결 1(WO-10a-1)·정체 1(PHASE-02), upward-fetch 에 PHASE-01 주입 확인. 배송 형상(미커밋 사유물 제거 사본) 전 스위트 green. §7-⑤ 계보 검사는 ID 기준이라 WO-10a-1 의 `parent: PRO-10` 관례(10 ⊃ 10a-1)는 통과 — 도메인 아닌 계보가 파티션 키라는 [PRO-05] 문법의 재확인.
- [2026-08-24][ADR-44]: CI 를 **컨테이너 정본 + 워크플로 얇은 래퍼**로 이전([TOOL-27] 신설: `scripts/ci.js` + `Dockerfile` + `docker-compose.yml`). 게이트 순서와 [PRO-11] 차단 정책이 `harness.yml` 의 YAML 안에만 살아 있었다 — 그 지식은 **GitHub Actions 안에만** 존재하므로, 어답터가 다른 CI 를 쓰거나 로컬에서 같은 검사를 돌리려면 YAML 을 손으로 번역해야 하고 번역본은 곧 원본과 어긋난다. `next.md`(생성 뷰)·`tools-index`(생성 블록)에서 이미 적용한 **로직 1벌** 원리를 CI 에 적용한 것이다. 동기는 비용이기도 하다: Actions 는 public 레포만 무료이고 **어답터는 대개 private** 이라 분당 과금 대상이다 — 컨테이너는 어디서든 무료다. 판정 기준: **워크플로 2개를 통째로 지워도 게이트가 살아야 한다.** 검증은 단언이 아니라 실행으로 했다 — CI 체크아웃을 클론으로 시뮬레이션해(미커밋 사유물 0) 컨테이너 체인이 exit 0 · 전 게이트 통과 · `handoff-linter` CLARIFY 를 비차단 경고로 표면화함을 실측([ADR-26]의 "테스트 환경 ≠ 배송 환경" 반복 회피). 갈림길 둘: ①워크플로 **완전 삭제**는 기각 — 상류는 public 이라 무료이고 PR 체크는 남는 게 낫다. 래퍼는 3줄이라 어답터가 지우는 비용이 0 이다. ②Dockerfile 의 `COPY` 는 **의도적으로 없다** — 레포를 구우면 어답터마다 이미지가 갈라지고 로컬 편집마다 재빌드가 필요하다. 마운트하면 이미지 1개가 모든 레포에서 재빌드 없이 돈다.
- [2026-08-25][ADR-45]: compose 서비스의 실행 지점을 `command` → **`entrypoint`** 로 옮김([TOOL-27]). `docker compose run SERVICE ARGS` 의 추가 인자는 `command` 를 **교체**하고 `entrypoint` 뒤에는 **이어붙는다** — 스크립트 경로가 `command` 에 있으면 CI 가 주는 `--range` 가 경로를 밀어내 `node --range` 가 되어 죽는다(실측: CI 첫 런 `node: bad option: --range`, exit 9). 더 중요한 것은 **왜 로컬에서 안 잡혔는가**다: 검증을 `run --rm harness` 로만 돌렸고 CI 는 `--range` 를 준다 — 배송 호출 형태가 아닌 단순형으로 검증한 것이라 [ADR-26]("테스트 환경 ≠ 배송 환경")의 **같은 실수를 CI 이전 작업에서 반복**했다. 교훈은 "컨테이너를 돌려 봤다"가 아니라 **"CI 가 실제로 치는 명령 그대로 돌려 봤다"**여야 통과라는 것이다. 부수 확인: 같은 커밋에서 누설 게이트가 TOOL-27 카드의 METHODOLOGY 미등재를 잡았는데, 이것도 호스트에선 미커밋 spike 의 FAIL 에 묻혀 **클론 검증에서만** 드러났다 — 배송 형상 검증이 한 세션에 두 번 값을 했다.
- [2026-08-25][ADR-46]: 하네스 컨테이너 파일을 **어답터 루트와 충돌하지 않는 이름**으로 이전(`Dockerfile`→`ci/Dockerfile` · `docker-compose.yml`→`docker-compose.harness.yml` · 루트 `.dockerignore` 폐지) + `SYNC_RULES` 편입. [ADR-44]가 이 둘을 **레포 루트에** 둔 것은 어답터 형상을 안 본 결정이었다 — 어답터 레포 루트에는 대개 자기 앱의 컨테이너 파일이 이미 있다(실측: 한 어답터의 루트 `Dockerfile` 은 Railway 배포용 멀티스테이지 빌드, `.dockerignore` 는 그 앱 것). 결함은 둘이었다: ①**전달 공백** — 두 파일이 `classifyPath` 에서 `null`(템플릿 소유 아님)이라 어답터에 **영영 전달되지 않는데**, 카드는 `docker compose run --rm harness` 를 쓰라고 적었다. 배송되지 않는 명령을 문서가 약속한 것이다. ②**더 심각 — sync 가 남의 배포를 깨는 경로**: `harness.yml` 은 sync 라 어답터에 자동 반영되는데, 새 harness.yml 은 compose 를 부르고 그 compose 는 전달되지 않으므로 **어답터의 CI 가 조용히 깨진다**. ①을 "SYNC_RULES 에 `Dockerfile` 추가"로 풀었다면 `--apply` 가 Railway 배포 파일을 덮어썼을 것이다 — 규칙 추가가 아니라 **개명**이 답인 이유다. 판별식: *템플릿이 레포 루트의 관례적 이름을 점유하면 안 된다 — 루트는 어답터의 공간이다.* [LSN-17](형상 사각지대)의 새 축이며, 어답터 팔의 `env` 축이 못 잡았다(팔의 사본은 상류 레포라 앱 파일이 없다 — 팔에 "어답터 고유 루트 파일" 픽스처가 없는 것이 잔여 공백이다).
- [2026-08-25][ADR-47]: 당위 축 '절 구조' 칩이 규범 **헤딩을 `esc()` 만 거쳐** 넣던 경로를 `plain()`(인라인 마커를 해석해 벗김)으로 교체 + 어답터 팔 `data` 축에 규범 헤딩 픽스처 추가. 상류 규범 헤딩엔 백틱이 없어 [ADR-35]의 마커 게이트를 통과했고, **실어답터 평면에서 발현했다**(`결정: DB 접근은 raw \`pg\` Pool` · `결정: 루트 단일 Dockerfile + \`PACKAGE\` 빌드 인자` — 6건). [LSN-17]이 "실데이터에서만 참인 사실은 여전히 하류 제보로 온다"고 남긴 **잔여 위험이 실제로 실현된 첫 사례**다: 팔의 `data` 축은 상류가 *지어낸* 대안 형상이라, 상류가 상상하지 못한 형상(헤딩 속 코드 스팬)은 픽스처에 없었다. 갈림길: `prose()` 를 쓰면 칩(`<code>`) 안에 칩이 중첩되므로, `proseInline` 으로 파싱한 뒤 태그만 걷는 `plain()` 을 신설했다 — **마커 문법은 여전히 한 벌**이다(파서를 복제하면 [ADR-37] 부류가 재발한다). 카드 규범대로 픽스처를 추가했고 **가드가 무는지 먼저 확인했다**([ADR-40] 절차): 수리 전 코드에서 정확히 6건 발현, 수리 후 0건.
