# [PRO-22] 테스트 축 — 실행과 영수증

## 1. 배경 — [PRO-21]이 푼 것과 하류가 아파하는 것은 다르다

[PRO-21]은 §5.5의 진단("재사용 실패 = 가시성 문제")을 받아 층 2(카탈로그)를 채웠다. 그러나
2026-09-25 **어답터 9곳 읽기 전용 감사**(서브에이전트 4 + 핵심 주장 3건 직접 재확인)에서 반복된
사고는 "있는 픽스처를 몰라 새로 만들었다"가 아니었다. **"검사가 안 돌았다"** 와
**"통과 주장을 확인할 수 없다"** 였다.

| 관측 (어답터 9곳, 익명 집계) | 곳 수 |
|---|---|
| 제품 테스트 전체가 자동(CI 또는 강제 훅)으로 도는 곳 | **2** |
| 호스티드 CI 가 꺼졌거나(비활성·과금 차단) 비용 때문에 삭제된 곳 | 4 |
| 상류 CI 템플릿([TOOL-27] 체인)을 쓰는데 그 체인이 **하네스 스위트만** 도는 곳 | 4 |
| WO 증거의 수치가 에이전트 수기(실행 기록과 무연결) — 사후 거짓 판명 1 · gitignore 경로를 영수증으로 인용 1 | 대부분 |
| `evidence:` 필드 사용률 (표본 3곳) | 0/154 · 0/374 · 1/44 |
| "아무것도 검사하지 않는 초록불" 교훈 — mock 이 실제보다 얇음 · 픽스처가 코드의 가정을 복사 · no-op 타입체크 | **7** |
| 알려진 실패가 '기준선'으로 상주 (최장 32일 · 최대 44건) | 4 |
| CON-00 이 있는 곳 — 전부 실제와 어긋남 / 가이드에만 약속되고 미작성 | 4 / 4 |

규모도 곁일이 아니다: 최근 커밋 중 테스트 파일을 건드린 비율이 곳에 따라 **약 10~60%** 다.

**설계는 이미 이것을 예언했다.** §2.3: *진짜 Raw(테스트 로그)는 CI 가 생성하는 외부 신호*이고
evidence 가 target 을 승격한다(Promotion 화살표). 실태는 `raw/evidence.md` 가 받는 것이 하네스 게이트
한 줄뿐이고 `health` 에서 EVD 도메인이 미사용이다 — **약속↔결과 화살표가 제품 테스트에 연결된 적이
없다.** 게다가 상류 CI 템플릿의 초록불이 "제품이 괜찮다"로 읽히는 착시를 만든다([LSN-17] 문법의
재현: 상류 형상에서는 하네스 = 제품이라 이 구분이 안 보인다).

외부 근거(2025~2026)도 같은 방향이다 — 에이전트의 테스트 우회는 측정된 현상이고
([ImpossibleBench](https://arxiv.org/abs/2510.20270): 모순 테스트에서 프런티어 모델 약 50% 우회),
에이전트 커밋은 mock 을 더 많이 넣으며([MSR 2026](https://arxiv.org/abs/2602.00409)),
AI 도입은 처리량↑·안정성↓와 함께 가고 자동 테스트가 그 완충 역량으로 꼽힌다
([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)).

**하류가 이미 발명한 기계적 방어** (교훈 글이 아니라 코드로 버틴 것): DB 부재를 skip 이 아닌 실패로
(`REQUIRE_*` 환경 플래그) · 외부 정답표 오라클 · 수동 변이 확인("변이 red N") · 아키텍처 래칫 테스트 ·
"테스트가 실제로 안 돌면 실패"하는 리포터. 상류의 일은 새 발명보다 **이것들의 표준화**다.

## 2. 가설 — 설문([WO-22a-1])으로 판정할 것

- **H1 실행**: 어떤 검사가 실제로 막는지가 평면 어디에도 *선언*돼 있지 않아서, 꺼져도 모른다.
- **H2 영수증**: 증거가 실행 산출물이 아니라 에이전트 수기라 사후 검증이 안 된다.
- **H3 기준선**: 알려진 실패에 담당·만료가 없어 상주한다.
- **H4 약화**: 테스트 약화(삭제·skip 추가·단언 순감·스냅샷 대량 갱신·mock 교체)가 diff 에 보이는데 아무도 묻지 않는다.
- **H5 카탈로그**: 층 2 가시성은 2차 문제다 — 재생성 사고 빈도가 H1~H4 보다 낮다.

## 3. 채택안 (초안 — 설문 후 확정)

새 기둥·도메인·티어 0. 선언 1개 + 기존 표면 4곳 확장.

1. **검사 선언** — `adapter.json` 에 `checks` 키([ADR-29] 설정 표면: 어답터 소유·상류 불가침).
   ```jsonc
   // (예시)
   "checks": [
     { "name": "unit", "cmd": "pnpm test", "blocking": true, "runs_on": ["pre-push"], "covers": "api·web 단위" },
     { "name": "e2e-smoke", "cmd": "pnpm e2e:smoke", "blocking": false, "runs_on": ["manual"] }
   ]
   ```
   `ci.js` 가 하네스 체인 뒤에 선언된 제품 검사를 돈다. 선언 부재는 **무기입**(INFO)이지 0 이 아니다([ADR-23]·[ADR-28] 문법).
2. **영수증** — `ci.js` 가 검사마다 한 줄(커밋·검사명·exit·소요·파싱 가능하면 통과/실패 수)을 raw 에 남긴다.
   **사람도 에이전트도 타이핑하지 않는다.** `work-close` 는 `evidence:` 가 영수증(커밋·검사명)을
   인용하는지 CLARIFY([PRO-15] 문법). `health` 는 차단 검사별 **최신 영수증 나이**를 INFO 로 —
   영수증이 끊기면 꺼진 CI 가 보인다.
3. **약화 표면화** — 범위 diff 에서 테스트 파일 삭제 · skip 류 추가 · 단언 순감 · 스냅샷 N줄 이상 갱신을
   나열하고 CLARIFY(비차단). WO 증거에 사유 한 줄이 있으면 통과.
4. **기준선 만료** — `checks[].known_failures: [{id, reason, owner, until}]`. 만료 초과를 CLARIFY.
5. **카탈로그 일반화** — [TOOL-28] 의 스캔 루트·주석 접두사를 설정으로 + [PRO-21] §6 미결 1(init 의 CON-00
   삭제→스켈레톤). **우선순위 최하** (H5).

구현 순서 1 → 2 → 3 → 4 → 5. 각 단계는 [ADR-40] 절차(가드를 먼저 물린다)로, 어답터 팔([TOOL-26])에
**비-JS 제품 형상**을 추가해 검증한다.

## 4. 분할원리 점검 ([PRO-04])

(a) 검증 신호 없는 시스템은 없다 ✓ · (b) 기존 칸에 들어간다 ✓ — 선언 = 설정 표면(`adapter.json`),
영수증 = `verification/raw`(EVD), 대조 = `work-close`·`health`, 약화 = `ci.js` 체인 단계.
[PRO-21] §5 의 `TEST` 도메인 기각은 **유지**한다.

## 5. 하지 않는 것

- ⛔ **런타임 훅으로 테스트 파일 보호** — 외부 트렌드의 주류 처방이지만 [ADR-08] 재제안 차단 대상이고
  재개 조건(배치 승인 단위 훅)이 미충족이다. 사후 게이트 + CLARIFY 로 푼다.
- ⛔ **제품 검사 실패로 하네스 CI 차단을 기본값화** — `blocking` 은 어답터가 검사별로 선언한다. 상류 기본값은
  관찰(한 어답터는 CI 를 의도적으로 관찰 전용으로 판정했다 — 그 판정을 덮지 않는다).
- ⛔ **숨은(holdout) 테스트** — 비용이 크고 소규모 어답터에 과잉.
- ⛔ **층 3 체크박스 강제** — 9곳 중 실사용 2곳. 긴 명세 문서는 쓰이지 않는다.
- ⛔ **커버리지 수치 게이트** — 개수·수치는 질의 대리 지표가 못 된다.

## 6. 판정 절차 · 성공 바

- **판정**: 설문 2곳(통합 테스트 인프라가 가장 두터운 어답터)에서 H1~H5 별로 사례·반례를 모은다.
  두 곳 모두 사례 → 채택 단계로 · 한 곳만 → 보류(관측) · 둘 다 반례 → 기각 사유를 이 문서에 보존.
- **성공 바(어답터 팔)**: 선언된 제품 검사를 끈 형상에서 `health` 가 영수증 공백을 표면화한다 ·
  테스트 삭제 diff 에서 CLARIFY 가 발현한다 · 선언 부재 형상에서 크래시 0.

## 7. 미결 (인간 판단)

- **로컬 영수증은 "시스템 Append"인가** ([PRO-11]): 호스티드 CI 가 없는 곳이 절반이라 영수증은 로컬
  러너(pre-push·컨테이너)에서도 나와야 한다. "러너가 생성하고 에이전트가 타이핑하지 않는다"가 본질이라는
  해석 vs "raw 는 CI 만" — 설문 답을 보고 판정.
- 영수증을 raw 한 파일에 둘지(현행 `evidence.md`) 검사별로 나눌지 — 크기 회전([PRO-18])과 함께 본다.
