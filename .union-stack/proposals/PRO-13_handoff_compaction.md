# [PRO-13] HANDOFF 압축 프로토콜

## 1. 요지
HANDOFF가 토큰 제한에 걸리는 것은 용량 문제가 아니라 **라우팅 실패의 증상**이다 — HANDOFF에
남을 자격이 없는 기록(결정·교훈·과정 서사)이 갈 곳으로 가지 않고 적체된 것. 따라서 해법은
상한 확대가 아니라 ⑴ 작성 시점의 **기록 가치 결정 트리** 의무화, ⑵ **압축(추상화) 4칙**,
⑶ 이를 강제하는 **예산 게이트**다.

## 2. prev.md는 되살리지 않는다 (선결 확인)
sprint/_GUIDE.md가 이미 실측 후 폐지했다 — *"no session ever did, and the file never existed —
the discipline was removed rather than automated."* 과거 세션 복원은 **git history**
(`git show HEAD~1:.union-stack/sprint/HANDOFF.md`)와 ledger가 담당한다. 운용 인스턴스에
prev.md가 남아 있다면 구버전 템플릿 잔재이므로 본 프로토콜로 수렴한다.
인간 가독 연속 로그가 필요하면 `verification/raw/` append(기존 지침)를 쓴다.

## 3. 기록 가치 결정 트리 (세션 종료 시, 항목 단위로 위에서부터 첫 매칭)
`where_to_record`의 ROUTES 표를 **HANDOFF 작성 절차로 승격**한 것이다:
```text
① git·코드·평면 문서에서 재도출 가능한가?      → 기록하지 않는다 (과정 서사·시도 나열·도구 출력 원문)
② 전략적 분기점(방향 전환+근거)인가?           → project/HISTORY.md
③ 결정+근거(전술, 작업/ZFS 단위)인가?          → archive_ledger.md (ADR)
④ 같은 계보 2회 이상 반복된 함정인가?          → reference/lessons/LSN-* (레포 특정만; 환경 특정은 사적 메모리)
⑤ 하네스 규칙 변경 제안인가?                   → proposals/PRO-*
⑥ 미착수 작업(다음 세션 이후의 큐)인가?        → next.md
⑦ 다음 세션 부트스트랩에 필요한가?             → HANDOFF.md — 단, ID 포인터 형태로만
⑧ 위 어디에도 해당 없음                        → 기록하지 않는다. "아까움"은 근거가 아니다.
```
①과 ⑧이 본 제안의 핵심이다 — **버릴 자격의 명문화.** 유일 원천이 평면·git에 있으면 HANDOFF의
복제는 가치가 아니라 드리프트 위험이다.

## 4. 압축(추상화) 4칙 — HANDOFF에 남는 항목의 형태
1. **포인터 우선**: 실체가 평면 문서에 있으면 ID만 남긴다(`[WO-01a-2]` 스타일). 내용 복제 금지.
2. **측정은 숫자+재현 명령 1줄**: 서사·과정 삭제. (예: `pytest 448/448 — node scripts/x.test.js`)
3. **논의는 결론 1줄 + Why 1줄**: 그 이상은 ③ ledger행이라는 신호다.
4. **체류 상한 3세션**: 같은 항목이 HANDOFF에 3세션 이상 생존하면 잘못 라우팅된 것 — lessons/ledger로 승격하거나 폐기한다.

## 5. 예산 게이트 (handoff-linter — smell-linter 확장 또는 신설)
[PRO-11]의 4값 결과와 차단 정책을 전제로 한다. **이 게이트는 어떤 판정으로도 커밋·세션 종료를
막지 않는다(REJECT 없음)** — 세션 종료 시점의 차단은 인계 자체를 유실시키는 최악의 마찰이므로,
불완전한 HANDOFF가 없는 HANDOFF보다 낫다. 모든 판정은 표면화이며, 미해소분은 다음 세션
부트스트랩에서 첫 화면에 뜬다(그 세션이 여유 있을 때 정리):
- **5부 검사**(요약·변경 ID·다음 진입점·미결/주의·검증 상태). 빈 부는 `— 해당 없음` 토큰 권장 —
  누락 시 **CLARIFY**(경고 표면화, 비차단). 미기입과 해당없음의 구별(SPIKE C6의 이 맥락 한정 채택).
- **토큰 예산**: `context-budget.js`로 측정, 기본 상한 **1,500 tok**(선례: [PRO-10] 시나리오 본문 상한.
  값은 승인 시 인간이 확정). 초과 → **CLARIFY** — "자르라"가 아니라 "§3 트리로 라우팅하라"는 신호.
- **체류 상한(§4-4)·next.md 중복은 지표다**: health/린터가 개수만 표시(advisory). 항목 단위 강제 없음 —
  §3 트리는 작성자가 머리로 도는 필터이지 항목별 심사 서식이 아니다. 강제점은 예산 하나로 족하다.

## 6. 반증 조건
- 예산 게이트 도입 후 인계 실패(다음 세션이 진입점을 복원 못 해 재탐색)가 **증가**하면 상한이 과도한 것 → 상한 재조정, 게이트는 존치.
- 결정 트리 도입 후에도 HANDOFF 비대가 재발하면 병인은 라우팅이 아니라 세션 스코프(한 세션에 너무 많은 작업) → 별도 제안으로 이관.
- **마찰 회귀**: `session-friction.js` 기준 세션 종료(인계) 의도의 왕복 비용이 도입 전보다 늘면
  프로토콜이 의례가 된 것 → 검사 항목 축소(예산만 남기고 5부·중복 검사 제거).

## 7. Split-principle check
(a)/(b) 해당 없음 — 신규 기둥·도메인·파일 없음. 기존 가이드의 규율을 게이트로 조작화 + 린터 확장뿐. (prev.md 부활 없음 — §2.)
