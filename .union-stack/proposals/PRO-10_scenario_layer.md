# [PRO-10] 시나리오 층

## 1. 요지
작업 유형별 절차(결함 수정·기능 추가·적응 이행·구조 리팩토링·그린필드)를 **버전관리되는 카드**로 두고,
**인간이 고르고 에이전트가 실행한다.** 신규 도메인·평면 없음 — TOOL 카드에 `kind: scenario`를 추가한다.

## 2. Split-principle
신규 기둥/도메인이 아니다. 시나리오는 스킬이고, TOOL은 이미 "재사용 실행 자산의 사용 계약"이며 카드
형식이 적용조건·부정스코프를 강제한다. 따라서 (b) "기존 셀에 안 들어감"에 해당하지 않는다 —
[PRO-08]의 확장이자 [PRO-09] 이후 CNJ 도메인을 거부한 논리와 동일하다.

## 3. 형식 (요약)
- frontmatter 필수: `version`(정수) · `status` · `activation`(기본 `manual`) · `entry_gate` ·
  `exit_criteria` · `reviewed` · `evidence[]`
- 스킬 본문 필수 절: `## 절차`(단계 사이 검증 삽입) · `## 종료 조건`(기계 검증 가능)
- **금지**: `roleDefinition`(페르소나는 코딩에서 최악 피해), 본문 >1,500 tok(간결이 포괄을 약 4배 우세)
- **증거 없는 Active 금지**: `evidence[]`가 비면 `Draft`를 벗어날 수 없다
- 강제: `smell-linter.js` 확장(`kind: scenario`일 때 위 규율 검사)

## 4. 아키타입 (상한 5, 출발 1)
확립된 분류를 채택한다 — 결함수정(*corrective*) · 기능추가 · 적응이행(*adaptive*) ·
구조리팩토링(*perfective*, 범위 `기회적|캠페인`) · 그린필드(ISO 12207 *Development* 층위, 명시 필요).
사용자 원안의 "유지보수성 강화"는 리팩토링과 같은 칸이므로 **범위 파라미터로 흡수**한다.
2~3개가 최적이고 4개↑는 급감하므로 **5는 상한이지 출발점이 아니다.**

## 5. 검증 (E6, `eval/PROTOCOL.md` §3-bis)
3-arm: ①무시나리오 ②시나리오 강제 ③자가 선택. **②−①=내용의 가치, ②−③=오분류 비용**(문헌 부재).
첫 대상은 **결함 수정** — 실측 동형성 1.00(n=8)으로 절차가 안정돼 있고, 동시에 Feedback-Bandwidth
가설상 *효과 없음이 예보되는* 자리라 가장 반증당하기 쉽다(포퍼: 위험한 시험을 먼저).

## 6. 반증 조건 (층 전체)
시나리오 3개가 각각 A/B를 거쳐 **어느 것도 ①을 못 이기면 이 층을 폐기**한다.
전례가 있다: Cursor Custom Modes 제거(2025-11-21), Roo Code 아카이브(2026-05-15) — 양쪽 다 사유 미공표.

## 7. 정직한 예보
기대값을 낮게 잡는다: 큐레이션 스킬의 **소프트웨어 공학 도메인 이득은 +4.5pp**(전체 평균 +16.6pp의 1/4),
84과제 중 16개가 음수(최악 −39.3pp), "부실한 계획은 무계획보다 해롭다"(16,991 궤적).
설명 가설(Feedback-Bandwidth)은 이 레포가 E1 T2에서 **8개월 먼저 관측**한 것과 같다 —
인라인으로 보이는 지식엔 하네스 한계기여가 0이었다.
